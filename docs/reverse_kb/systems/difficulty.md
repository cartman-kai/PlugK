# 难度系统

本文整理游戏难度的全局状态、1.05 静态交叉引用，以及为 plugK 增加自定义难度时的实现边界。当前结论主要来自 1.05 IDA 静态分析；尚未确认的功能语义和 2.01 对照项保留在 `research_queue.md`。

## 版本与全局变量

| 版本 | 难度全局变量 | 原版内部值 |
| --- | --- | --- |
| 1.05 | `dword_54C7A8` / `0x0054C7A8` | `0..3` |
| 2.01 | `0x0057D360` | `0..4` |

内部编号与玩家难度名称见 [版本差异](../versions.md)。

1.05 的 `dword_54C7A8` 是进程级全局整数。当前 IDA 数据交叉引用中只有 `sub_4A2EA0` 写入该变量；其余引用均为读取。`sub_4A2EA0` 在确认创建角色时，从 UI 控件 159 的 `+0xC4` 字段取得当前难度值。

## 1.05 选择界面与流程状态

来源：IDA 静态分析。

| 函数/地址 | 行为 |
| --- | --- |
| `sub_4A2E30` / `0x004A2E30` | 创建角色界面的控件点击分发；控件 159/179 调整难度，控件 160 确认创建 |
| `sub_4A3050` / `0x004A3050` | 按 `+1/-1` 循环难度值 |
| `sub_4A31B0` / `0x004A31B0` | 把难度值写入控件 159，并用文本 ID `difficulty + 115` 刷新显示字符串 |
| `sub_4A2EA0` / `0x004A2EA0` | 确认创建；把控件 159 的 `+0xC4` 写入 `dword_54C7A8` |
| `sub_4A3410` / `0x004A3410` | 创建角色界面初始化，注册控件 157、159、160、161、179 |

`sub_4A3050` 存在两套循环范围：

- `dword_55788C == 0` 时只循环 `0..2`。
- `dword_55788C != 0` 时循环 `0..3`。

这表明“真正的战斗”在原版界面中受一个额外解锁状态控制。若加入第五项，不能只修改全局变量，还需要同时处理循环边界、显示文字、解锁策略和确认创建路径。

### `sub_4247E0` 的角色属性缩放

来源：IDA 静态分析、GB2312 编码的 `game_file/mb/assets/RolePrivate.txt` 数据表验证、游戏内观察。

`sub_4247E0(this, column_index)` 读取 `RolePrivate.txt` 中的角色属性。程序使用从 0 开始的列索引，因此代码中的 9/10/11/13 对应文本文件按自然数计数的第 10/11/12/14 列，分别为 `HP`、`AT`、`DF`、`命中率`。

已验证样本：

- `RolePrivate.txt` 中“僵尸”的基础 HP 为 200。
- 选择“真正的战斗”（内部难度 3）后，plugK 游戏内观察到僵尸 HP 为 400。
- `200 * 2.0 = 400`，与 `sub_4247E0` 的难度 3 分支完全一致。

因此 `0x004247F9` 所在逻辑可以确认是敌人/角色的 HP、攻击、防御和命中率难度倍率入口，而不只是一个尚未识别的通用模板读取。为自定义难度设计 `EnemyStatMultiplier` 时，可以优先考虑在该函数边界处理；仍需确认玩家角色、友方单位、召唤物等是否也会经过同一函数，避免把只希望作用于敌人的倍率扩展到其他角色。

### `sub_47F740` 的高级宝石合成失败门槛

来源：IDA 静态分析、Python 数据表解析。模板文件为 GB2312/GBK 系列编码、Tab 分隔的 `game_file/mb/assets/PropUpgrade.txt`。该文件包含严格 GB2312 不支持的繁体扩展字符，Python 应使用 `encoding="gbk"` 或 CP936 兼容解码器读取。

Python 解析得到 121 条数据记录，前五个表头为：

```text
組合    結果    失敗損失    附註    目標寶石
```

`結果` 字段可以是单一结果代号，也可以用 `结果代号*权重*结果代号*权重...` 表示多个随机候选。例如：

```text
Z1*60*Z2*40
```

表示 60% 选择五色雨花石 `Z1`、40% 选择七彩雨花石 `Z2`。如果显式权重合计小于 100，未覆盖的随机区间是模板自身的普通失败率；`失敗損失` 字段决定普通失败时损失的原料。

`sub_47F740` 是宝石合成/升级流程的一部分。当前静态控制流可整理为：

1. 读取 `PropUpgrade.txt`，根据参与合成的宝石匹配一条升级规则。
2. 按 `結果` 字段中的候选和权重执行 `rand()%100`，随机选出本次准备生成的宝石；若随机数没有落入任何候选权重，则进入普通失败路径。
3. 在 `PropMdl` 表中按结果代号查询记录，并读取自然列号 9 的“等级”字段；结果代号位于自然列号 10。
4. 根据当前难度设置允许生成的最高结果等级。
5. 如果随机结果的等级高于该门槛，则把输出状态写成 `-1`，不进入后续移除原料和创建结果宝石的路径。

| 难度 | 内部编号 | 允许的最高结果等级 |
| --- | ---: | ---: |
| 低 | 0 | 7 |
| 中 | 1 | 8 |
| 高 | 2 | 9 |
| 真正的战斗 | 3 | 15 |
| 1.05 未知非 0/1/2 值 | 其他 | 15 |

因此 `0x0047FC7D` 的 `7/8/9/15` 不是直接参与随机数判定的失败百分比，而是高级宝石结果的难度等级上限。调用方 `sub_4BEE20` 进一步确认了两种不同的失败状态：

- 普通失败：`PropUpgrade.txt` 的结果权重没有覆盖本次 `rand()%100`，输出状态为 `1`，按 `失敗損失` 处理原料，并显示文本 ID 311。
- 难度阻断：已经随机选中一个结果，但它的 `PropMdl.等级` 超过当前难度门槛，输出状态为 `-1`，显示另一条文本 ID 310；静态路径不会进入原料移除和结果创建逻辑。

对带显式权重且权重总和不超过 100 的规则，可以写成：

```text
普通失败率 = 100% - 所有候选权重之和
难度阻断率 = 等级高于当前门槛的候选权重之和
成功率     = 等级不高于当前门槛的候选权重之和
```

例如 `Z1*60*Z2*40` 中，`Z1` 等级 7、`Z2` 等级 8：

- 低难度门槛为 7：60% 成功生成 Z1，40% 被难度阻断。
- 中难度门槛为 8：两个结果都允许，合计 100% 成功。

又如 `Z1*Z1*Z1 -> Z2*20`，Z2 等级为 8：

- 模板本身有 80% 普通失败率。
- 低难度剩余的 20% Z2 结果还会被门槛 7 阻断，因此无法成功生成 Z2。
- 中难度允许 Z2，成功率为 20%，普通失败率仍为 80%。

`PropMdl.txt` 当前可见的高阶结果最高到等级 11（像素之星），所以 1.05 “真正的战斗”使用门槛 15 时不会阻断当前表内结果。

自定义难度参数应使用类似 `GemUpgradeMaxResultLevel` 的业务名称，不应命名成 `GemUpgradeFailurePercent`。如果还要直接控制模板固有失败率，应另设结果权重倍率或失败率参数，不能把两种失败机制混为一个配置值。

## 为什么不能直接写入值 4

1.05 原版没有为值 4 建立统一语义。把 `dword_54C7A8` 直接写成 4 会得到混合行为：

- `sub_452200`、`sub_447E30`、`sub_47D850`、`sub_47F560`、`sub_47F740` 等使用“其他值”或 `>2` 分支，表现接近原版最高难度。
- `sub_4247E0` 对未知值不做难度属性缩放，退回接近难度 1 的路径。
- `sub_47E5A0` 只显式处理 1、2、3，值 4 不缩放，与难度 0 相同。
- `sub_423FB0` 只在值等于 3 时应用最高档修正，值 4 会漏掉该修正。

因此“值 4 可保存”不等于“第五难度可用”。在没有逐一接管上述分支前，不应把 4 直接作为 1.05 的运行时难度。

## 建议的 plugK 实现模型

### 逻辑难度与原版难度分离

建议增加 plugK 自己的逻辑难度状态：

```text
custom_enabled
profile_id
base_game_difficulty
schema_version
```

自定义难度启用时，1.05 的 `dword_54C7A8` 仍写入 `base_game_difficulty`，首个实现建议固定为 3；plugK 再对已确认的系统施加额外规则。这样未接管的原版逻辑至少稳定地保持“真正的战斗”，不会因未知枚举值进入互相矛盾的默认分支。

### 参数按业务含义设计

不要把 IDA 中的立即数和分支编号直接暴露为配置。建议按系统分组：

```ini
[CustomDifficulty]
Enabled=1
ProfileId=plugk_custom_1
BaseGameDifficulty=3

[CustomDifficulty.Combat]
EnemyStatMultiplier=...
ResourceGainMultiplier=...
DeathExpProgressLossPercent=...
DeathGoldRecoverPercent=...

[CustomDifficulty.Drop]
MoneyChanceMultiplier=...
ItemChanceMultiplier=...
Type10Weight=...
Type20Weight=...
Type30Weight=...
GemLevelOffsetMin=...
GemLevelOffsetMax=...

[CustomDifficulty.Progression]
GemUpgradeMaxResultLevel=...

[CustomDifficulty.AI]
BehaviorChanceMultiplier=...
```

`sub_4247E0` 已确认是 `RolePrivate.txt` 部分战斗属性的难度倍率入口，可以作为 `EnemyStatMultiplier` 的首个候选 Hook。`sub_47F740` 已确认可以用 `GemUpgradeMaxResultLevel` 表达高级宝石合成门槛。属性入口的作用对象范围，以及 `sub_419000` 的 `+0x32D`、`sub_47E5A0` 的 `+0x5C` 语义确认前，仍不宜把更细的属性参数固定为公开配置。第一阶段可只开放统一敌人属性倍率、宝石合成结果等级上限、掉落、死亡惩罚等已能清楚描述的参数。

掉落类型权重应接受三个非负权重并在模块内部归一化，不强制用户填写总和 100。概率和百分比参数应在加载时限定范围；倍率应设置合理上限，并在调试日志中输出最终生效值。

### 选择入口

有两种可行入口：

1. 先通过 `PlugK.ini` 或启动器选择自定义难度，游戏内仍选择“真正的战斗”。这是最小风险方案。
2. 在游戏创建角色界面加入第五项。需要 Hook `sub_4A3050`、`sub_4A31B0`、`sub_4A2EA0`，并提供自定义名称渲染；原版 `difficulty+115` 的文本索引不能假定存在第五个合法字符串。

第二种方案还要明确第五难度是否始终显示、是否要求先通关，以及左右切换时与原版 `dword_55788C` 解锁状态如何交互。

### 存档与兼容

建议不要把自定义值 4 直接写进 1.05 原版存档字段。更安全的做法是：

- 原版存档和 `dword_54C7A8` 保存 `base_game_difficulty`。
- plugK 按存档保存 `schema_version`、`profile_id` 和是否启用自定义难度。
- 找不到 plugK 扩展元数据、禁用 Mod 或配置版本不兼容时，回退到原版基准难度。
- 明确存档采用“引用当前 profile”还是“保存创建时参数快照”。为了避免更新配置后旧存档难度静默变化，建议至少保存 profile 指纹并提示差异。

现有 [`inheritance.c`](../../../plugK/src/inheritance.c) 会修改 1.05 `0x0049E39F` 的比较立即数。该位置实际比较流程对象 `+0xC8` 与 3，且 `sub_49E260` 会把难度写入 `+0xC8`；自定义难度开发前必须动态复核当前把立即数改为 5 的行为，避免与新的持久化方案冲突。

## 推荐实施顺序

1. 用硬件写入断点确认 `0x0054C7A8` 的创建、读档、切图和通关生命周期。
2. 保持原版全局值为 3，仅加入只读调试日志，记录全部关联 Hook 的命中与输入输出。
3. 先实现掉落与死亡惩罚两个语义较清晰的自定义参数组。
4. 动态确认 `sub_4247E0` 的作用对象范围、其他初始化字段、AI 概率和脚本 `AddItem` 分支后，再逐组开放参数。
5. 最后决定是否修改原版创建角色界面；界面不是验证核心规则的前置条件。
