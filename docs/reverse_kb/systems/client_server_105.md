# 1.05 client/server 遗留架构

本文记录《刀剑封魔录》1.05 `ComeOn.exe` 中 `sub_4890A0` 附近的 client/server 遗留设计，并区分“逻辑上的服务端/客户端分层”和“可跨机器联机的网络传输”。

## 结论

`sub_4890A0` 不是“是否具有联机功能”的布尔判断函数。它是一次会话初始化入口：先安装或创建全局角色数据对象，再根据两个不同的模式来源装配角色模拟端、数据路径对象和本地玩家创建流程。

当前 1.05 发布程序确实保留了明显的 client/server 术语、包格式和处理边界，但已确认的正常运行方式是同一进程内的组合模式：游戏逻辑以 server 侧为权威端生成状态/包，client 侧消费这些包并更新表现与本地状态。当前没有证据表明该程序包含可用的局域网或互联网传输层。

这个判断的置信度较高，但范围限定为当前 IDA 打开的 1.05 `ComeOn.exe`。不能据此排除开发期曾有另一个 client/server 可执行文件、未发布 DLL 或被移除的网络模块。

来源：IDA 静态分析、2026-08-09 对当前 1.05 PE 导入表和二进制字符串的只读检查。尚未对强制修改各模式后的运行效果做动态验证。

## `sub_4890A0` 的实际职责

函数签名当前可近似理解为：

```text
Session_Init(session, optional_role_data)
```

主要步骤：

1. 若传入已有角色数据对象，则写入 `dword_558AC4`；否则分配 `0x378` 字节并调用 `sub_47D3E0` 构造，再执行新角色数据初始化。
2. 调用 `sub_43B2B0` 做公共初始化。
3. 先检查 `sub_471C40()` 返回的数据路径记录/回放状态。
4. 非回放状态下，再检查 `sub_408AB0()` 返回的程序角色模式，设置窗口标题并创建对应对象。

因此此前地址表只把它描述成“创建角色对象”并不完整；角色对象只是其前半段职责。

## 两个不要混淆的模式来源

### `sub_408AB0`：程序角色模式

`sub_408AB0` 在当前 1.05 中只有两条指令：

```asm
mov eax, 1
retn
```

它更接近编译时选定的 `GetRoleMode()` / `IsServerBuild()`，而不是检测网络环境或读取联机设置。它还被多处游戏规则调用，用来决定是否执行权威状态修改；这进一步说明其语义是“当前逻辑端是否为 server”，不是“网络是否可用”。

`sub_4890A0` 中可见的模式矩阵：

| `sub_408AB0()` | 窗口标题 | 创建本地 server/分发对象 | 创建 client 数据路径对象 | 自动提交本地角色创建 |
| ---: | --- | --- | --- | --- |
| `0` | `DaojianClient` | 否 | 是，control=`0` | 否 |
| `1` | `DaojianServer` | 是 | 是，control=`1` | 是 |
| `2` | `ComeonServer` | 否 | 是，control=`1` | 否 |
| `3` | `OnlyServer` | 是 | 否 | 否 |

当前发布程序固定返回 `1`，所以正常启动走 `DaojianServer`。这里的标题不是玩家可选择的联机模式，而是内部架构角色的调试痕迹。plugK 查找主窗口时兼容 `DaojianServer` 也与这一实际路径一致。

### `sub_471C40`：数据路径记录/回放模式

`sub_471C40` 只返回 `dword_557AC0`。它与上述角色模式完全独立：

- `0`：正常路径。
- `1`：`sub_471D90` 在继续本地消费包之前，会把包长度和内容写入 `FILE *Stream`。
- `2`：`sub_4890A0` 强制使用 `DaojianClient` 分支；其它调用点也跳过部分 server 初始化，表现符合包回放/客户端测试模式。

当前数据库中，`dword_557AC0` 没有可达的普通 setter 交叉引用；析构路径只会把它清零。相关 `Stream` 也没有正常打开和赋值的直接交叉引用。这一子系统很可能是开发期记录/回放设施或已裁剪功能，不能把值 `2` 直接解释为可连接远端服务器的网络客户端模式。

## 数据如何在本进程内流动

已确认的本地链路如下：

```text
脚本/调试命令（例如 #CreateClient）
    -> sub_4702B0
    -> sub_487E50
    -> 在 CriticalSection 内追加到 dword_558430 队列
    -> 游戏状态机取出并生成/分发二进制包
    -> CDataPathProperty / sub_471D90
    -> sub_4702D0 在本进程内消费包
    -> 创建玩家对象或更新对象状态
```

`sub_487E50` 的实现只分配一个 `0x1C` 字节命令对象、复制字符串、写入参数，然后进入临界区把对象追加到全局容器。这里没有 socket、进程间通信或远端地址。

`sub_4702D0` 是明显的 client 包处理器：其中日志字符串包括 `Client :BEGIN_Packet_Create_Client` 和 `Client :Packet_Create_Client`，并按包类型处理创建 client、对象状态、场景/UI 更新等。它直接调用本进程中的对象创建和状态更新函数。

这说明“client”和“server”并非纯粹无意义的字符串；游戏内部确实按网络游戏常见方式划分了权威逻辑和包消费逻辑。但在发布程序里，两端通过内存队列/对象调用闭环，而非网络传输。

## 为什么当前版本不能据此认定支持联机

对当前 `ComeOn.exe` 的 PE 导入表检查只发现 `WINMM`、`KERNEL32`、`USER32`、`GDI32`、`WINSPOOL`、`ADVAPI32`、`COMCTL32`、`ole32`、`DDRAW` 和 `DSOUND`。没有：

- `WSOCK32.dll` / `WS2_32.dll` 及 `socket`、`connect`、`bind`、`listen`、`send`、`recv`。
- DirectPlay / `DPLAYX.dll`。
- WinINet 等互联网 API。

考虑到程序导入了 `LoadLibraryA` / `GetProcAddress`，又额外对二进制可打印字符串检查了上述 DLL/API 名称；只命中了 `CreateClient` 和四个模式标题，没有发现网络 DLL 或网络 API 名称。因此“通过显式导入或按名字动态加载常见 Windows 网络栈”的可能性也很低。

另一方面，程序中确实存在 `PACKET_*`、`Client :...`、`#CreateClient`、100 槽位的 client/server 管理结构和线程安全队列。这些是网络化架构或开发期多人方案的遗迹，但“保留包协议和两端逻辑”不等于“保留可用传输层”。

## 使用 plugK 实现局域网的可行性

结论是“技术上可行，但属于高风险的大型功能”，不能把它实现成单一地址上的联机开关。plugK 已经被注入 `ComeOn.exe`，能够安装 MinHook、创建工作线程并调用 Win32 API，因此有能力自行提供 Winsock 传输层；真正困难的是恢复远端输入、玩家槽位、初始状态和场景切换的一致性。

最有价值的复用边界是 `CDataPathProperty` 虚表 `off_529710` 的 `+0x0C` 项：该项指向 `sub_471D90(this, packet, length)`。它收到明确的包指针和长度，按需记录后调用 `sub_4702D0` 在 client 侧消费。这意味着局域网实现可以复制原游戏已经形成的二进制包，不必为每个角色和场景对象重新设计状态序列化。

建议采用“主机权威”结构：

```text
主机（保留模式 1）
    server 模拟 -> 原游戏包 -> 本地 sub_4702D0
                         \-> plugK 复制并发送给远端

客户端（实验性模式 0）
    网络线程收包 -> plugK 私有线程安全队列
                 -> 游戏主线程取包
                 -> sub_471D90 / sub_4702D0

客户端输入
    逻辑动作/命令 -> plugK 上行消息 -> 主机主线程
                  -> 原 server 命令或玩家槽位入口
```

网络线程不得直接调用 `sub_4702D0` 或修改游戏对象；这些函数会操作 UI、场景和全局容器，应在已经确认的游戏主线程更新边界投递。plugK 当前把大量初始化放在 `DllMain` 中，联机模块也不应在 loader lock 内执行 `WSAStartup`、建连或等待线程，应延迟到首个安全帧或独立初始化线程。

当前已经具备的条件：

- 原程序有 server 权威逻辑、client 包消费者和二进制包长度边界。
- server/会话对象存在 100 个槽位式结构，至少说明设计并非只容纳一个逻辑 client。
- `#CreateClient` 能通过本地命令队列触发创建流程，可作为研究加入会话的入口。
- plugK 的注入、版本检测、MinHook 和配置框架足以承载原型。

尚未解决且决定项目成败的边界：

- 远端输入如何携带 client ID 进入主机的 server，而不是控制主机本地角色。
- 新 client 的槽位分配、角色数据、create-client 包字段和断线销毁流程。
- 加入时的完整初始快照；仅转发连接后的增量包无法还原已存在对象和场景状态。
- 场景切换、读档、暂停、随机数、掉落、任务和 UI 决策的权威端边界。
- 包序号、可靠性、顺序、拥塞/限速、超时和版本/资源一致性检查。
- 模式 `0` 是否能在发布版中完成纯 client 初始化；当前只能确认静态分支存在，尚未动态验证。

建议用以下门槛逐步决定是否继续：

1. 先 Hook `sub_471D90` 做纯记录，确认包长度、频率、生命周期以及缓冲区在返回后是否失效。
2. 做单进程延迟回放，验证复制后的包能在后续主线程帧安全调用 `sub_4702D0`。
3. 启动两个本机进程，先做只观看的远端 client；若模式 `0` 无法稳定加载场景，应在此阶段停止直接复用方案并重新评估。
4. 只打通一个远端角色的移动输入与 create/disconnect，再扩展攻击、物品和技能。
5. 最后才增加局域网发现、主机/加入 UI、存档保护和断线处理。

因此，plugK 能承载局域网原型，且现有包边界让它比从零改造普通单机游戏更有希望；但在完成“双进程旁观 client”和“远端输入绑定到独立槽位”两个验证之前，不能承诺可玩的完整联机。

## 安全的后续验证边界

若继续动态调研，建议先做观察而不是直接把 `sub_408AB0` 的返回值改成 `0/2/3`。大量游戏规则函数把它当作 server 权威性门控，强改可能导致对象只渲染不更新、初始化对象缺失或静默破坏存档流程。

优先验证项：

1. 正常启动时在 `0x004890A0`、`0x0048919F`、`0x004891C8`、`0x004891D1`、`0x004891EE` 下断，确认实际进入模式 `1` 的完整组合路径。
2. 在 `sub_487E50` 与 `sub_4702D0` 下断，记录 `#CreateClient` 从文本命令进入本地队列、再形成 type 1 create-client 包的顺序和线程 ID。
3. 观察 `dword_558430` 队列的生产者/消费者是否都属于同一进程；静态结果已经确认数据结构位于本进程全局内存。
4. 若能找到开发版、独立 server/client 程序或同年代源代码，再对照其 `sub_408AB0` 等价实现与缺失的传输层。

## Hook 边界

- 不应把 `sub_4890A0` Hook 成简单的联机开关；它同时负责角色数据、server 分发对象、client 数据路径对象和本地玩家创建。
- 不应仅修改窗口标题分支来切换角色模式；真正的权威逻辑门控由 `sub_408AB0` 的多个调用点共同决定。
- `sub_487E50` 是共享的进程内命令队列入口。若未来 Hook，应检查所有调用来源，不能只按 `#CreateClient` 假定其用途。
- 当前没有发现网络连接点，因而暂时不存在可安全复用的“远端地址/端口”Hook 边界。
