# 商店商品生成与优化

## 原版生成流程

1.05 使用 `sub_453530`，2.01 使用同构函数 `sub_45F660`。函数先取得或创建商店对象，并清空其中 50 个商品槽位，再按 `RandProp` 字段生成固定商品和随机商品。

| `RandProp` 运行时字段 | 用途 |
| ---: | --- |
| 17 | 固定商品 ID 列表，以 `*` 分隔 |
| 18 | 固定商品总格数 |
| 19 | 随机商品 ID 范围 |
| 20 | 随机商品总格数 |

固定商品先写入槽位，随机商品随后追加。原版仅对 Type 20–29 使用 `rand() % 5 + 1`，其余类型数量为 1。来源：1.05、2.01 IDA 静态分析。

## 当前优化规则

`OptimizeShop` 统一控制回复套餐、分类排序及 ID 4–15 无限售卖。Hook 先完整调用原版生成函数，再处理实际生成的商品；不再修改 `RandProp` 模板。

- 回复类按 Type 10–19 判断。同 ID 只保留一组 `1/5/10` 套餐。固定和随机来源统一去重，优先复用先出现的固定商品对象；随机独有的回复 ID 同样生成套餐。
- 投掷类按 Type 20–29 判断。所有原有格子、数量及属性均保留，不限制同 ID 的格数，不改随机数量。
- 其他商品保留原有格子、数量及属性。
- 排序顺序为回复类、投掷类、其他类；每类按 ID 升序、同 ID 按数量升序。只在生成后排序，不在每次购买后重新整理。
- 购买后仅 ID 4–15 保留，不区分固定或随机来源；其他 ID 按原版销毁并清空槽位。此判定只看 ID，不看物品类别。

按实际非回复商品格数与去重后的回复 ID 数量计算容量。若三档总格数超过 50，统一移除回复类的 10 档；仍超出则移除 5 档。每种回复 ID 原本至少占一个格，因此对于合法的原版 50 格输出，一档总能容纳，不需要移除任何非回复商品。

容量示例：40 格非回复商品、4 个回复 ID，三档需要 52 格，裁掉 10 档后为 48 格；47 格非回复商品、2 个回复 ID，最终使用一档，共 49 格。

## 对象生命周期与 Hook 边界

`shop_optimization.c / Mod_shop_opt_init` 独占生成函数 Hook。两版入口均为 `ECX=商店管理器`、栈参数为角色对象，C 实现以带占位 EDX 参数的 fastcall 包装兼容 thiscall。仅在原函数成功返回后处理对应商店；不 Hook 随机数函数。

去重时保留同 ID 的第一个回复对象，通过原物品虚表第一个函数、参数 1，释放多余回复对象。补齐套餐复用游戏的“复制物品到商店第一个空格”函数，该函数创建独立的 0x3C 字节对象，复制模板、数量和附加字段，并通过游戏 CString 赋值管理字符串引用。不能用 plugK 的 malloc/free 或直接浅复制来替代游戏对象管理。

复制函数是直接调用，不新增 Hook。其构造路径会消耗游戏随机数，但发生在本轮原版商品生成完成后，不重抽、不改变本轮已经生成的投掷类和其他商品。后续随机序列不保证与关闭优化时逐项一致。

`shop_inf_stock.c` 保留原有购买后销毁判断 Hook，按 ID 4–15 跳过销毁和清空槽位。旧的固定商品指针登记表已删除。两个模块不拦截玩家出售物品、背包整理或其他通用物品创建入口。

## 物品叠加与单格上限

回复叠加仍由 `EnableConsumableStack` 控制，宝石叠加由 `EnableGemStack` 控制。商店套餐不读取这两个开关，也不读取玩家单格上限。

`ItemStackLimitEnabled=0` 时，默认上限由 9 改为 10；启用自定义上限时仍使用配置值，范围为 1–127，已有值不迁移。配置默认启用自定义上限 99，这一设置未改变。

1.05 入包函数 `sub_47EF40` 会循环处理剩余数量；数量设置函数 `sub_47CED0` 对可叠加物品按上限截取并返回余量，对不可叠加物品写入 1 并返回余量。因此关闭回复叠加或设置较低上限时，商店的 10 个套餐仍应交由原版入包流程拆分；背包无空位时走原版落地路径。此结论来自静态分析，游戏内扣款、拆分、满包行为仍需验证。

旧配置迁移规则保留：`OptimizeItem` 映射到 `EnableConsumableStack`；`OptimizeItem`、`InfStock`、`EnableSort` 中任一开启即映射为 `OptimizeShop=1`，随后删除三个旧键。

## 历史问题：RandProp 索引偏移

旧实现直接读取 `RandProp` 时漏掉内部容器的 +8 偏移，导致无法生成套餐。1.05 查询链为 `sub_4D0A60 -> sub_4D2570`，2.01 为 `sub_4E5750 -> sub_4E74A0`。两版包装函数均先执行 `add ecx, 8`，因此相对外层表，ID 索引数量位于 +8，记录指针数组位于 +28。外层表地址分别为 `0x00548760`、`0x00578D18`。当前实现处理生成结果，已不依赖这一模板读取逻辑。

## 验证

使用 `tests/run-shop-x86.cmd` 运行 x86 回归检查。测试包含生产源码，模拟游戏对象复制与释放，覆盖固定/随机回复 ID 去重、随机独有 ID、三类升序排序、非回复对象和数量不变、容量裁剪、ID 4–15 边界及默认/自定义上限。回归检查与 Release x86 构建已通过；它们不替代游戏 ABI、CString 或画面验证。

两版对象复制与销毁路径已完成 IDA 静态核对。用户已反馈本次修改在游戏内验证通过；未提供具体游戏版本及逐项测试记录，因此不将该反馈扩展为两版全部边界场景均已验证。以下清单保留用于后续回归：

1. 使用新 DLL 重启游戏并触发商店重新生成。确认同一回复 ID 只有一组套餐，容量充足时为 1、5、10。
2. 确认投掷物保留多个格子及原随机数量；检查三类商品的 ID、数量升序。
3. 分别购买 ID 4–15、投掷物和其他固定商品。仅 ID 4–15 应保留。
4. 在默认上限 10、自定义上限低于 10，以及关闭回复叠加的情况下购买 10 个套餐，核对总获得数量和扣款。
5. 检查满包、刷新、切换商人及 50 格容量场景。
