# 2.01 client/server 内部包管线

本文记录 2.01 `ComeOn.exe` 中 `DaojianServer`、`DaojianClient` 以及相关本地命令/二进制包路径。结论来自当前 PyGhidra 项目的静态分析；模式 `0/2/3` 的实际启动效果、线程边界和完整包字段仍需动态验证。

## 结论

2.01 的 `DaojianServer` 不是独立的纯服务端进程，而是同一进程内的组合模式：

- 服务端管理器维护逻辑对象、角色记录和更新流程。
- 数据路径对象接收二进制包，并在 Client 侧创建或更新对象、场景和表现。
- 两者通过本进程内的函数调用、虚函数调用和内存对象连接，没有发现已启用的 TCP/IP、DirectPlay 或 WinINet 传输层。

因此，当前更准确的描述不是“服务端把对象写入客户端”，而是：服务端先更新自己的逻辑状态；需要同步表现时，按操作类型构造二进制增量包；数据路径对象把包交给 Client 包处理器；包处理器再查找或创建 Client 侧对象并写入对应字段。

这不是每帧把所有对象字段做一次完整快照。不同操作使用不同包类型和字段，部分逻辑也直接通过本进程内的对象或虚函数调用完成。

## 模式矩阵

`0x004985C0` 是会话初始化入口。它先创建或接收角色数据对象，再根据回放状态和 `0x0047CAD0()` 的返回值组合内部对象。

| `0x0047CAD0()` | 窗口标题 | `0x678` 字节服务端管理器 | `0x1FD0` 字节数据路径对象 | 数据路径 control |
| ---: | --- | --- | --- | ---: |
| `0` | `DaojianClient` | 否 | 是 | `0` |
| `1` | `DaojianServer` | 是 | 是 | `1` |
| `2` | `ComeonServer` | 否 | 是 | `1` |
| `3` | `OnlyServer` | 是 | 否 | — |

当前 201 程序中的 `0x0047CAD0` 只有 `mov eax, 1; ret`，正常启动固定进入 `DaojianServer`。

在模式 `1` 中：

1. `0x00498960` 分配 `0x678` 字节对象，并调用 `0x00494080` 构造服务端管理器。构造函数初始化多组 100 项槽位式表。
2. `0x004988F0(this, 1)` 分配 `0x1FD0` 字节数据路径对象，并通过 `0x0047EEF0` 把对象的 control 字段 `this+0x2C` 设为 `1`。
3. `0x00494AF0` 把角色路径和初始参数写入服务端管理器，设置待处理状态。

`DaojianClient` 只创建数据路径对象，`OnlyServer` 只创建服务端管理器。两者都不是当前发布程序的正常游戏组合；是否能在被强制选择后稳定启动，尚未动态确认。

## 两类本地数据流

### 文本命令队列

`0x00498A50` 在 `0x00589498` 临界区内读取全局命令队列，逐项调用 `0x00494D30`。队列节点至少包含：

- `node+0x14`：命令字符串。
- `node+0x18`：命令参数或来源参数。

`0x00494D30` 目前确认会识别 `#CreateClient`，解析三个参数，然后调用 `0x00493C10` 创建服务端侧的角色/对象记录，并继续调用后续初始化函数。

`0x00498A50` 是命令队列消费者，不是二进制包的通用消费者。`0x00497370` 会在更新过程中调用它；随后在正常条件下调用 `0x00494C40` 更新服务端管理器。

### 二进制状态包

服务端更新入口 `0x00494C40` 会：

1. 根据服务端管理器 `this+0x65C` 的待处理状态调用 `0x00494200`，处理场景/角色路径及相关对象状态。
2. 通过 `0x00494B50`、`0x00494AB0` 遍历服务端管理器的槽位记录。
3. 对需要更新的记录调用 `0x00493340`。

创建角色或对象时，`0x00493C10` 会先调用 `0x0049A940` 加入对象管理器，然后调用 `0x00493B40`。`0x00493B40` 在栈上构造一个固定布局的创建类包，再调用服务端对象虚表的第一个函数指针将包交给下游。当前静态代码没有显示“把服务端对象内存原样复制到 Client”。

## 包入口和记录格式

数据路径对象的包入口位于 `0x00480350`，该入口由 `0x00552934` 的虚表数据引用。入口会把包指针和长度传给 `0x0047E720`。

在独立的记录状态 `DAT_00588908 == 1` 下，入口先调用 `0x00480410`。该函数按以下顺序写入记录流：

```text
uint32 packet_length
byte   packet_data[packet_length]
```

时间值变化时，代码还会构造一个 6 字节的特殊记录包。这个记录流用于本地记录/回放，不能解释成网络协议。

`0x00480350` 的正常路径仍然继续调用 `0x0047E720`，因此记录行为不会替代包消费行为。

## 已确认的包结构特征

当前只能确认“包类型和若干字段位置”，还不能给出完整的协议结构体：

- `0x0047E720` 使用 `packet[0]` 作为主类型。
- `packet[1]` 以 16 位值读取，部分路径把最高位作为标志，低位用于对象/记录索引。
- `packet[3]` 在多个类型中作为子类型或操作码。
- `0x004F9130` 会根据包类型检查 `packet[1]` 或 `packet[3]`，用于过滤不属于当前数据路径的数据。
- `0x00493B40` 构造的创建类包把 `packet[0]` 设为 `1`、`packet[3]` 设为 `1`，并把调用参数写入 `packet[1..2]`；其余字段来自服务端对象的 ID、位置、状态和标志字段。
- 包入口显式接收长度，记录模式也显式保存长度；因此包边界不是依靠对象大小或字符串结束符确定。

### 主类型的静态观察

以下是 `0x0047E720` 中已看到的处理，不代表完整字段定义：

| `packet[0]` | 静态观察 |
| ---: | --- |
| `1` | 创建或重建 Client 侧对象；子类型 `0/1` 有不同初始化路径，并处理对象模板、位置、分组和名称等字段。 |
| `2` | 按对象索引查找记录，并调用对象虚表 `+0x20` 的处理函数。 |
| `3` | 按对象索引处理状态/动作类子类型；当前看到 `0x33`、`0x34`、`0x65`、`0x66` 等分支。 |
| `4` | 把多个 16 位字段传给对象处理函数 `0x00433C50`；具体字段语义待动态确认。 |
| `5` | 把子类型传给对象处理函数 `0x004297B0`；具体语义待动态确认。 |
| `7` | 对特定对象执行动作/触发处理，调用 `0x0043F5E0`；找不到符合条件的对象时输出 `PACKET_OBJ_TRIBLD` 调试信息。 |
| `8` | 调用 `0x0049B630`，执行 Client 对象管理器中的移除/清理路径。 |
| `9` | 调用 `0x00477CF0`，处理场景或地图相关数据。 |
| `0xA`、`0xB`、`0xC`、`0xD`、`0xE` | 进入全局状态、回调、会话或 UI 相关路径，完整映射待确认。 |

例如，类型 `1` 的 Client 处理路径会调用 `0x0049A940` 创建 Client 侧对象，再调用 `0x00434330`、`0x0042A620`、`0x00442010` 和 `0x00421460` 写入对象的数值、分组或名称相关字段。这说明 Client 侧确实有自己的对象更新过程，但它接收的是操作包，而不是服务端对象的原始内存块。

## 对“循环刷新到 Client”的准确理解

“服务端对象先更新，循环时把结果刷新到 Client”只能作为高层概括，不能作为实现细节。更准确的顺序是：

```text
输入、脚本或服务端规则
    -> 更新服务端对象/槽位状态
    -> 对需要表现同步的变化构造类型化二进制包
    -> 数据路径对象的虚函数入口（packet, length）
    -> 可选的记录流（仅记录模式）
    -> 0x0047E720 按 packet[0] 分发
    -> 查找或创建 Client 侧对象，并更新场景/UI/表现
```

需要注意三点：

1. 服务端更新循环 `0x00494C40` 会遍历逻辑记录，但不能据此推断每个字段都会在每次循环中生成一个完整快照包。
2. 有些操作通过服务端对象虚表或本进程函数直接触发，包只是其中一种传递状态的方式。
3. `0x0049A940`、`0x00494AF0` 等函数存在多个调用来源，不能仅凭函数名或一次调用就认定它们是 Server 专用入口。

## 对大型 Mod 的 Hook 边界

推荐保留正常的 `DaojianServer` 组合模式，把 Server 侧作为规则入口，同时保留原版 Client 数据路径：

- 战斗、属性、技能、掉落、AI、脚本结果和对象生命周期等规则，优先在实际规则函数或服务端更新来源处 Hook。
- 需要改变 Client 可见状态时，优先复用原版对象 setter、包生成或状态通知路径；只改服务端内存而不触发下游更新，可能造成数值、对象和 UI 不一致。
- 不要把 `0x0047CAD0` 改为 `3` 作为大型 Mod 的常规方案。`OnlyServer` 缺少数据路径对象，不能替代“只 Hook Server 逻辑”。
- 不要把 `0x0047E720` 当成服务端规则入口；它是集中式 Client 包处理器。若在此观察或修改包，必须保留原始分发和主线程边界。
- 修改 `0x00494AF0`、`0x0049A940` 或其它共享函数时，应按调用来源或返回地址限定范围。当前 `0x00494AF0` 至少同时来自会话初始化、脚本/标志处理和运行时路径。

## 尚未确认

- `0x00493B40` 使用的服务端虚表第一个函数的完整实现，以及包是否经过额外的本地队列。
- `0x00480350`、`0x0047E720` 的实际线程 ID、调用频率和包缓冲区生命周期。
- 创建、移动、动作、删除和场景包的完整字段类型、长度和对象索引复用规则。
- 强制模式 `0/2/3` 后的最小启动行为，以及回放状态 `DAT_00588908` 的全部设置来源。
- 是否存在少量不经过二进制包、直接共享对象或全局变量的 Client 更新路径。

来源：PyGhidra 对 2.01 `ComeOn.exe` 的静态反编译、反汇编、字符串和交叉引用检查。当前项目导入表包含 `DDRAW.DLL`、`DSOUND.DLL` 等本地组件，但未见 `WS2_32.DLL`、`WSOCK32.dll`、DirectPlay 或 `WININET.DLL`；这支持“当前发布程序使用进程内包管线”的判断，但不能排除尚未发现的手工实现或外部模块。
