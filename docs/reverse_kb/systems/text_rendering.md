# 文字渲染与内置颜色控制码

本页记录游戏通用文字输出函数、默认颜色字段和字符串内置颜色控制码。来源：1.05/2.01 IDA 静态分析、2.01 颜色常量读取、plugK 提示文字实机验证。

## 通用文字输出

| 版本 | 函数 | 默认颜色 |
| --- | --- | --- |
| 1.05 | `sub_4B25A0` / `0x004B25A0` | 文字绘制对象 `this + 0x60` 的 `COLORREF` |
| 2.01 | `sub_4C58F0` / `0x004C58F0` | 文字绘制对象 `this + 0x60` 的 `COLORREF` |

两个版本的函数都会先以 `this + 0x60` 调用 `SetTextColor`。字符串存在内置控制码时，函数会为该行改用固定颜色，并在送入 `TextOutA` 前删除控制码；没有控制码时继续使用对象默认颜色。

## 2.01 字体创建与生命周期

2.01 的 `sub_4C7640` / `0x004C7640` 是全局字体初始化函数。它从资源根目录读取 `Font.txt`，以 `SystemParametersInfoA(SPI_GETNONCLIENTMETRICS)` 得到的系统菜单字体为 `LOGFONTA` 模板，然后逐行覆盖字体参数并调用 `CreateFontIndirectA`。来源：IDA 静态分析、2026-07-19 x32dbg 原版 2.01 进程验证。

| Font.txt 字段 | 运行时行为 |
| --- | --- |
| 字段 1 `nHeight` | 按 `-MulDiv(value, LOGPIXELSY, 72)` 写入 `lfHeight` |
| 字段 2 `fnWeight` | 实际乘到 `lfWidth`，没有写入 `lfWeight`；表头名称与实现不一致 |
| 字段 3 `lpszFace` | 复制到 `lfFaceName` |

生成的 `HFONT` 保存到 `0x0058C44C` 开始的 6 槽全局数组。当前 `Font.txt` 有 4 行数据；原版 2.01 正常显示中文时，x32dbg 确认前 4 槽为有效句柄、后 2 槽为零。`sub_4C6A80` / `0x004C6A80` 在资源管理器退出/清理时遍历 6 槽，对非空字体调用 `DeleteObject` 并清零。

2026-07-19 在原版 2.01 的 `0x004C77C0` 动态读取 `LOGFONTA`：四个字体槽的 `lfHeight` 依次为 `-12/-12/-24/-12`，共同参数为 `lfWidth=0`、`lfWeight=400`、`lfCharSet=DEFAULT_CHARSET(1)`、`lfQuality=DEFAULT_QUALITY(0)`。敌人名称记录的 `fnWeight=2` 仍然只执行 `0 * 2`，所以没有改变实际宽度或字重。`lfFaceName` 起始字节为 GBK `CB CE CC E5 00`（宋体）；NUL 后残留的 `Microsoft YaHei UI` 字节来自系统菜单字体模板，不属于最终字体名。

字体数组由三条共享 GDI 路径消费：

| 函数 | 行为 |
| --- | --- |
| `sub_4C5710` / `0x004C5710` | `SelectObject` 后调用 `GetTextExtentPoint32A` 测量文字 |
| `sub_4C5790` / `0x004C5790` | `SelectObject` 后调用 `DrawTextA` 绘制矩形/多行文字 |
| `sub_4C58F0` / `0x004C58F0` | `SelectObject` 后调用 `GetTextExtentPoint32A` 与 `TextOutA` |

三条路径均以文字对象 `this + 0x78` 的索引选择 `h[index]`。字体替换应保留该数组、字体索引、原字号和上述 GDI 测量/绘制链；推荐在 `sub_4C7640` 返回后按非空槽重建字体，而不是分别 Hook 三条高频文字函数或全局 Hook GDI API。当前 plugK 源码与知识库中没有其它功能 Hook `0x004C7640`。

`sub_4C5790` 与 `sub_4C58F0` 都通过 DirectDraw surface 虚表 `+0x44` 取得 HDC（`IDirectDrawSurface::GetDC`），绘制结束后通过虚表 `+0x68` 释放 HDC（`IDirectDrawSurface::ReleaseDC`）。两条路径在输出前均调用 `SetBkMode(hdc, TRANSPARENT)`；矩形路径在 `0x004C5897` 调用 `DrawTextA`，通用路径在 `0x004C5BB6` 调用 `TextOutA`。游戏没有把文字转换为自定义点阵字模或带 Alpha 的字形纹理，而是让 GDI 直接栅格化到游戏表面。游戏常用 16 位 RGB565 表面，因此现代轮廓字体在小字号产生的灰阶/抗锯齿边缘会再被量化，可能比原宋体更显得发虚、发灰或有彩边。来源：IDA 静态分析；16 位表面行为另见背包/技能渲染专题。

这不等于原版在 API 层使用纯点阵字体。`sub_4C7640` 使用普通 `CreateFontIndirectA`，没有自定义字库，也没有强制 raster/vector 输出精度；最终实际字体与字形栅格化方式由 Windows GDI 字体映射器决定。原版宋体的 `-12` 像素小字号与现代微软雅黑的度量、hinting 和抗锯齿结果差异很大；静态 IDA 可以确认上述调用链，却不能单独确认某次运行选择了字体文件中的轮廓还是嵌入位图字形。若需区分实际 realized font 类型，应在运行时对已选入 HDC 的字体检查 `GetTextMetrics`、`GetOutlineTextMetrics`、`GetTextFace` 和字体表数据。

## 支持的控制码

2.01 的颜色常量位于 `0x005751D8..0x005751F0`。`COLORREF` 按 `0x00BBGGRR` 存储，因此表中同时列出更直观的 RGB：

| 控制码 | 颜色 | 2.01 常量地址 | `COLORREF` | RGB |
| --- | --- | --- | --- | --- |
| `$G` | 绿色 | `0x005751D8` | `0x0050FF50` | `(80,255,80)` |
| `$Y` | 黄色 | `0x005751DC` | `0x0050FFFF` | `(255,255,80)` |
| `$B` | 蓝色 | `0x005751E4` | `0x00FF7878` | `(120,120,255)` |
| `$R` | 红色 | `0x005751E0` | `0x003232FF` | `(255,50,50)` |
| `$W` | 白色 | `0x005751EC` | `0x00FFFFFF` | `(255,255,255)` |
| `$H` | 灰色 | `0x005751F0` | `0x006E6A6A` | `(106,106,110)` |

`0x005751E8` 还保存 `0x00FF5050`，但 `sub_4C58F0` 的六个控制码分支都不读取它，当前不能视为可通过字符串调用的第七种内置颜色。

1.05 的 `sub_4B25A0` 静态确认识别相同的 `$G/$Y/$B/$R/$W/$H`，颜色表区域始于 `0x00545C48`；`$W` 已由技能重置提示实机验证为白色。本轮未重新逐字节读取 1.05 的全部六个常量，因此上表精确数值标注为 2.01 结论，不直接宣称两个版本的每个常量完全相等。

## 解析行为与使用边界

- 每个拆分后的文字行按 `$G -> $Y -> $B -> $R -> $W -> $H` 的优先级查找，只选择其中一种颜色。若同一行放入多个不同控制码，高优先级控制码会先命中。
- 控制码可以位于行内任意位置，但会影响整行，并在输出前被删除；推荐统一放在字符串开头，例如 `$W重置技能`。
- 颜色来自固定常量，不会修改文字绘制对象的 `this + 0x60`。这比长期改写共享默认颜色安全，因为同一文字对象可能同时服务物品名、NPC 名称和界面提示。
- `sub_4B25A0` / `sub_4C58F0` 是共享文字输出函数。需要 Hook 时必须复用现有物品名称模块的共享 Hook，不能由新功能再次安装 MinHook。
