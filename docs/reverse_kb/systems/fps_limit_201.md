# 2.01 主循环与帧率限制调研（fps_limit）

> 2026-08-02 于 IDA（2.01 ComeOn.exe）静态分析确认。plugK `fps_limit` 模块基于本文实现；
> 1.05 已完成静态对照并接入 Hook，详细记录见 `systems/fps_limit_105.md`。

## 结论摘要

- **HUD 的 fps = 每秒渲染帧数**：`sub_40E380` 每渲染帧调用一次，内部用 `timeGetTime`
  每 ~1 秒采样一次帧计数器（`dword_57937C`），采样值写 `dword_579388` 供 HUD 格式化显示。
- **模拟按固定步长 35ms 执行**：`dword_5741C8` = 0x23（只读常量，无运行时写入点），
  ≈28.6 模拟步/秒，用「落后 ≥ 35ms 就继续追」的 do-while 追赶循环维持。
- **渲染不受模拟步长限制**：渲染门控 `dword_5741D4` 初始值就是 1，只在检测到卡顿
  （帧间隔 > 200ms，距离目标帧数远时放宽到 1500ms）时清零——即**每一轮主循环迭代都完整渲染 + blt**。
- **主循环是 `PeekMessage` 纯自旋**，没有任何 Sleep/阻塞等待 → 现代 CPU 上渲染帧率无上限，
  每次渲染都是一次 ddraw blt。原版在 2003 年机器上靠渲染耗时自然限速；现代机器 + ddraw
  wrapper 后需要主动限速。
- **plugK 限速方案**：Hook 每帧函数 `sub_40B6C0` 入口，按目标帧间隔（0=桌面刷新率，
  -1=不限）Sleep + spin 补精度。等待时间会进入游戏自测的帧间隔 v3，模拟追赶循环自动消化，
  游戏速度不变，渲染帧率 = 目标帧率。

## 调用链

```text

  └─ sub_40B340   状态机：case 1/2/3/5 → sub_40B6C0；case 6 片头/过场（自带 Sleep(50ms)）
       └─ sub_40B6C0   每帧函数（游戏帧）

                    sub_44CBA0(dword_5787C4)   渲染
                    sub_504090(dword_5787C4)   光标/场景呈现

```

### fps 统计逻辑（`sub_40E380` 头部）

```c
++dword_57937C;                                    // 帧计数
dword_58DA3C = timeGetTime();
dword_579380 = dword_58DA3C - dword_58DA38;        // 距游戏开始时间
if (dword_58DA3C - dword_58DA38 > dword_579384 + 1000) {
    dword_579384 = dword_58DA3C - dword_58DA38;    // 记录采样时刻
    dword_579388 = dword_57937C;                   // fps = 上一秒渲染帧数
    dword_57937C = 0;
}
```

### 卡顿检测（`sub_40E0C0`）

帧间隔 `abs(v3)` 超过阈值即判定卡顿：距目标帧数 ≤ 20 帧时阈值 **200ms**，否则 **1500ms**。
超限路径：`dword_578D94 = now; dword_5741D4 = 0; return 0`（重同步，下次迭代恢复）。

## 限速实现要点（plugK fps_limit）

1. **Hook 点**：`sub_40B6C0`（0x0040B6C0）入口。理由：
   - 覆盖菜单/游戏全部调用它的状态；片头 state 6 不走此函数（自带 50ms Sleep，无需限）。
   - 入口 Sleep 的时长被游戏计入帧间隔 v3 → 模拟追赶循环自动补偿，模拟仍精确按 35ms 步进。
   - 渲染每轮迭代都执行，被节流后渲染帧率 = 目标帧率，HUD fps 直接显示目标值可验证。
   - 失焦时（`dword_578480`=0）渲染被游戏自身跳过，限速器继续 Sleep，后台 CPU 也下降。
   - 卡顿/切后台超过阈值时游戏走 200/1500ms 重同步路径，天然兼容。
2. **目标帧率解析**：配置 0 = 桌面刷新率（`EnumDisplaySettingsW(NULL, ENUM_CURRENT_SETTINGS, &dm)`
   的 `dmDisplayFrequency`）；-1 = 不限（不安装 hook 的等效行为）；其它值 clamp 到 15~400。
   首次进入 detour 时解析（避免 DllMain loader lock 风险）。
3. **计时**：QPC 基准；先 `Sleep` 粗等（`timeBeginPeriod(1)` 提高精度），剩余 < ~1.5ms 用
   spin-wait 补足，覆盖 120/144/240Hz（6.9/8.3ms 间隔）下的抖动。
4. **不累积延迟**：若本帧已晚于 `next`（渲染本身超时），直接把 `next` 重置为 `now + interval`，
   避免「追帧」产生一连串快速帧。
5. **风险点**：目标 fps < 28.6 时（帧间隔 > 35ms）模拟会被渲染钳制（每帧最多 ~1-2 步），
   表现为游戏略微变慢——与原版慢机器行为一致，可接受。

## 1.05 移植结论

1. 1.05 主循环为 `sub_401090`（`0x00401090`），`PeekMessageA` 自旋后调用状态机
   `sub_4043E0`（`0x004043E0`）。
2. 状态机 case `1/2/3/5` 唯一调用 `sub_404700`（`0x00404700`），该函数是 1.05
   对应 2.01 `sub_40B6C0` 的每帧函数；其唯一直接调用者为 `sub_4043E0`。
3. `sub_404700` 内确认了 `dword_544D9C = 0x23`（35ms）和同构的模拟追赶循环、
   `dword_544DA8` 渲染门控、卡顿重同步路径。
4. `sub_407320`（`0x00407320`）每次渲染计数，使用 `dword_548DA4`/`dword_548DB0`
   维护约 1 秒 FPS 采样；HUD 格式串含 `fps:%i`。
5. 1.05 应按相同模式 Hook `0x00404700` 入口；`__thiscall` 可继续使用当前
   `__fastcall(pThis, _edx)` Detour 适配。只需在 `plugK/src/fps_limit.c` 增加
   `ADDR_FRAME_FN_105 = 0x00404700` 并在版本分支选择该地址。
6. case 6 片头/过场路径在 `sub_4043E0` 内自带 `Sleep(0x32)`，不经过 `sub_404700`；
   这与 2.01 的状态 6 边界一致，不应把视频路径误判为普通渲染帧。

## 调研过程记录

- 起点：HUD 格式串 `.data:00574490`（`aDIIPlayerIIIIF`）→ 唯一引用 `sub_40E380`@0x40E5A6。
- 从 `sub_40E380` 头部解出 fps 统计口径（帧计数 + 1s 采样）。
- `sub_40E380` 唯一调用者 `sub_40B6C0` → 解出帧函数结构（模拟 35ms 固定步 + 每轮渲染），
  确认 `dword_5741D4` 门控语义（.data 初始 1，xrefs 确认只在卡顿路径清零）。
- `sub_40B6C0` 唯一调用者 `sub_40B340`（状态机）→ 唯一调用者 `sub_401340`（PeekMessage 自旋主循环）。
- `dword_5741C8` xrefs 为空 → 读 .data 确认初始值 0x23=35 且为只读常量。
- `sub_408E60` 为 WndProc（WM_ACTIVATE → `dword_578480` 激活标志），确认失焦只跳渲染、循环照跑。
- Sleep 全镜像搜索：仅状态机 case 6（片头）与 CRT 内部有 Sleep，游戏帧路径无任何 Sleep。
- 2026-08-02 以上结论登记为 IDA 注释（sub_40B6C0 / sub_40E380 / sub_40B340 / sub_401340 / dword_5741C8）。
