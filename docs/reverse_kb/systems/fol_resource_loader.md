# FOL 资源包加载系统

游戏的大多数数据资源（txt 表、mdl 模型、图片等）打包在 `.fol` 文件中。本文记录 fol 格式与游戏加载机制，结论对 Mod 工具（FolToolG 解包/打包）有直接影响。

## 结论速览

1. **游戏加载 fol 内资源按名字匹配，与索引条目的顺序完全无关**。
2. 打开资源时：按挂载的包列表顺序（`mb` → `slr` → `cj`）逐个搜索，包内对索引表做**线性、不区分大小写的字符串比较**，命中即返回；所有包都找不到时**回退到真实文件系统**（`fopen` 原始路径）。
3. fol 内索引条目的名字是**不带包名前缀的相对路径**（如 `player\Init.txt`），FolToolG 的解包路径逻辑正确。

## FOL 文件格式（1.05 / 2.01 相同，已用真实 mb.fol 验证）

```
[4B]  count | 0x80000000  有符号数，负数 = 加密（无符号时即 0x80000000|count）
[count × 0x88 (136B)]  索引表，每条目：
      [0x00, 0x80)  文件名 GB2312（最多 127 字符）
      [0x80, 0x84)  内容偏移（< dataBaseOffset 时 +dataBaseOffset）
      [0x84, 0x88)  内容大小
[...]                内容区，每文件用 TransformContent 加密
[count × 4]          key 表（尾部，紧贴 97×4 padding 之前）
[97 × 4]             padding（尾部）
```

索引解密（挂载时一次性）：每条目 34 个 dword，`v_i = v_i - key - 9·i³`。
内容解密（读取时）：`v_i = v_i - key - 99·i²`。
（与 FolToolG `FolCore.cpp` 的 `TransformIndex` / `TransformContent` 完全一致。）

## 加载机制

### 1. 启动挂载包

- 1.05：`sub_4CD6C0`（由 `sub_401120` 调用）。包名列表 `dword_55C200`（数组），数量 `dword_55C220`，链表尾 `dword_55C224`。
- 2.01：`FUN_004e25e0`（由 `0x00401483` 处调用）。包名列表 `DAT_0058d870`（数组），数量 `DAT_0058d87c`，链表头/尾 `DAT_0058d894` / `DAT_0058d898`，包计数 `DAT_0058d890`。
- 包名在启动代码里硬编码压入数组，2.01 位于 `0x00401456–0x0040147e`：`"mb"` / `"slr"` / `"cj"`（字符串 `0x00574110` 起），扩展名 `"fol"`（`0x0057411c`）。**挂载顺序 mb → slr → cj，先挂载的包优先命中**。
- 完整路径 = 基路径（`0x0058d8a0` / 1.05 `dword_55C230`）+ 包名 + `"."` + `"fol"` → 即 `mb.fol`、`slr.fol`、`cj.fol`（与游戏目录实际文件一致）。
- 包对象结构：`+0x04` FILE*、`+0x08` 索引表、`+0x0C` 条目数、`+0x10` key 表、`+0x14` 头部 count（2.01 在 `FUN_004e25e0` / 1.05 在 `sub_4CD6C0` 中填充）。

### 2. 解析 fol 头（挂载时）

- 1.05：`sub_4D4C50`；2.01：`FUN_004e9de0`。两版本逐行同构：
  - 读 4 字节 count；`count & 0x80000000` 判定加密，`& 0x7FFFFFFF` 取数量
  - `malloc(count × 0x88)` 读索引表
  - 加密时 `fseek(4 × (-97 - count), SEEK_END)` 读 key 表
  - 逐条目 34 个 dword 用 `-9·i³ - key` 解密（即 `v - key - 9·i³`）

### 3. 打开资源（每次读取）

- 1.05：`sub_4CDAB0(this, FileName, Mode)`；2.01：`FUN_004e29d0(this, path, ...)`。表格加载器（1.05 `sub_4D4C50` 的调用方，如 2.01 `FUN_004ec5b0` → `FUN_004e4780`）传入原始相对路径（如 `player\Init.txt`）。
- 流程：
  1. 无挂载包（count == 0）→ 直接 `fopen(FileName, Mode)` 磁盘打开。
  2. 遍历包链表：取包名，与请求路径做关系判断（1.05 用 `CString::MakeUpper` + 比较，即不区分大小写）；命中包后拼接（1.05：`sub_51DA27(SubStr, '\\')` 包名加 `\`）得到包内查找串。
  3. 包内查找 `sub_4D4AB0`（1.05）/ `FUN_004e9c40`（2.01）：以 0x88 步进线性遍历索引表，`strcmp`（不区分大小写，2.01 `FUN_00527ad0` 归一化 A-Z）比较条目名与目标串；匹配后返回 `+0x80` 偏移、`+0x84` 大小、对应 key 表项。
  4. 包内未命中或包列表遍历完 → 回退 `fopen(FileName, Mode)` 磁盘打开（**磁盘回退路径 = 原始请求路径，无包名前缀**）。
  5. 全部失败返回 -2（未找到）。
- 关键点：**包内查找是线性名字比较，索引条目排列顺序不影响结果**；只有「条目名唯一性」重要（同名条目先出现者胜出）。

## 对工具开发的结论（FolToolG）

- **不需要保持原始索引顺序**：打包时文件内容与索引条目可任意排列，游戏按名字找。`manifest.txt` 里保留的 `Index` 字段（originalIndex）对游戏无意义。
- **key 也不需要保留**：游戏把 key 表当纯解密密钥使用（读条目时取 `keys[i]` 用于内容解密），打包时全部重新随机即可，索引表与 key 表按下标一一对应即可。
- 简化方案：解包时按包内相对路径直接落盘（`player\Init.txt` → `outputDir\player\Init.txt`），不套 `assets/` 目录、不写 manifest；打包时递归扫描目录，相对路径（GB2312、`\` 分隔、不区分大小写注意同名冲突）作为条目名，随机 key。
- 磁盘直读方案（可选，需实测验证）：由于游戏有磁盘回退逻辑，把解包内容铺到游戏工作目录（原始相对路径，无包名层）后，**删除或改名对应 .fol 文件**（或确保包内无同名条目），游戏即可直接读磁盘文件，无需重新打包。注意回退路径是相对路径，目录结构须与包内相对路径一致；Steam 版工作目录行为需动态确认。
